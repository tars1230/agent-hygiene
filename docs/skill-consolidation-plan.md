# 纪律类 Skill 打包方案

> 2026-10-29 决策文档。回答一个问题：`diagnostic-tool-trust` 和
> `long-running-sample-discipline` 该**打包成一个**还是**各自独立**？
>
> 结论先行：**独立，但成对发布、共用一套机器门禁。**

## 一、结论与理由

| 方案 | 判定 | 理由 |
|---|---|---|
| **各自独立**（采纳） | ✅ | 两者解决**不同层**的问题，触发时机不同，失效后果不同 |
| 打包成一个 Skill | ❌ | ① 触发条件冲突（一个在「拿到结果时」触发，一个在「开始采样前」触发）② 体积膨胀、每次加载都读到不相关的那半 ③ 一个用坏了另一个跟着废 |
| 打包成「方案包」目录（次选） | ⚠️ | 保留独立性，但额外引入一层无收益的目录间接 |

### 为什么不能合并

**1. 触发时机不同 —— 这是硬理由**

| Skill | 触发时机 | 典型触发词 |
|---|---|---|
| `diagnostic-tool-trust` | **拿到工具输出之后**，准备下结论前 | 「这个结论可信吗」「交叉验证一下」 |
| `long-running-sample-discipline` | **开始采样之前**，设计采样方案时 | 「连续采样」「监控一下」「涨不涨」 |

合并成一个 Skill 后，agent 必须同时加载两套内容才能匹配其中一个触发词。

**2. 失效后果不同**

- `diagnostic-tool-trust` 失效 → **结论不可信**（可能误杀进程、误改配置）
- `long-running-sample-discipline` 失效 → **采样白跑**（浪费一次观察窗口）

前者要更严格、更常被检查；后者只在长跑任务里用。绑在一起会让「严格检查」被稀释。

**3. 内容几乎不重叠**

实测两个文件的判据集合交集：

```
diagnostic-tool-trust      9 条判据
long-running-sample-discipline  10 条判据
交集：0 条
```

一个是「**结果**可不可信」，一个是「**样本**够不够」。

### 为什么成对发布

它们是同一次事故的两个产物，共享同一套纪律来源：

```
grok 4.7 第三方复核（2026-10-29）
  ├─ 发现 7 个真 bug → diagnostic-tool-trust 的第 4/5/7 条
  └─ 发现速率不能写死 → long-running-sample-discipline 的第 2/3 条
```

所以：**独立安装、成对发布、共用一个门禁脚本**。门禁保证两边不会各自腐化。

## 二、两个 Skill 各自解决什么痛点

### `diagnostic-tool-trust`（工具可信度）

**痛点**：工具给出的错误结论**不会自己喊疼**。本机实测过的四类真实事故，
每一类表面都「看起来正常」：

| 事故 | 表面现象 | 实际真相 |
|---|---|---|
| 静默降级 | 静态分析报「native 100% 可达」 | 静态量的是「声明」环节；真跑时绑定失败只打 stderr 并返回默认值 |
| 排序类型语义 | `grep \| sort` 排十六进制 | 字符串序不是数值序（`0xBBBF0` < `0xFB4`）→ 结论完全相反 |
| 空报告全绿 | 门禁跑完报「PASS」 | `r.get(...) or 0` 把缺关键键兜成 0，**缺证据 ≠ 通过** |
| 副本分叉 | 仓库改好了，线上还是旧的 | 手工 `cp` 不同步，**且没有任何东西报错** |

**应用场景**：
- 要把某个工具的输出当结论用（而不只是扫一眼）
- 输出会导向**不可逆操作**（杀进程 / 删文件 / 改配置）
- 刚被第三方复核挑出问题，想知道自己哪里能改
- 要写进报告的**数字**

**独特价值**：**七道检查，每一道都要给证据**，而不是「我检查过了」。
其中「数字太干净 = 可疑信号」「结论对不代表推理链对（包括复核方的）」
这两条是踩过坑才有的，普通文档不会写。

### `long-running-sample-discipline`（长跑采样）

**痛点**：采样失败的三种死法都很安静：

| 死法 | 现象 | 后果 |
|---|---|---|
| 攒在内存里 | 进程被杀 → 样本全丢 | 白跑，且不知道丢在哪一轮 |
| 固定阈值判突跳 | `Δ>500` 就算突跳 | 匀速增长时**每段都被标成突跳** |
| 结论不绑窗口 | 「它每分钟涨 675」 | 三次实测 +1022 / +20 / **−3.2**，差两个数量级还变号 |

**应用场景**：
- 要连续采样同一指标并下趋势结论
- 判断「持续增长」vs「已稳态」——**两者处置完全不同**
- 需要产出可复核的时间序列

**独特价值**：
- **三态判定**（稳态 / 持续增长 / 突跳）而不是二态
- **速率中位数**代替固定阈值（抗单点尖峰）
- **逐目标 Δ**代替「某类对象数量没变」的倒推
- 结尾强制一句「不代表其他时段」——防止一个时段的观测被当成永久属性

## 四、使用前 / 使用后 的可量化区别

### A. 体检（只读）：信息增量

**使用前**——凭印象判断，只知道「电脑有点卡」。

**使用后**——`AgentHygiene-Weekly` 的实测算例（2026-10-26 05:10 那份）：

| 指标 | 数值 |
|---|---|
| 可用内存 | 1338MB / 16298MB，load 91% |
| commit | 29887MB / 37802MB |
| Top 家族 | explorer 5874.6MB / msedge 2682.7MB / WorkBuddy 1366.5MB |
| **CPU 判活** | explorer(13092) **CPU 155.3% → 在干活，别杀**；msedge(14000) 529.6MB 但 **CPU 0.0% → 空闲** |
| **趋势对比** | vs 10-22 基线：msedge **−1865MB 明显回落**，WorkBuddy **−1243MB 明显回落**，git.exe **+512MB 新增大户** |

关键区别：**光看内存分不出「该杀的」和「正在干活的」**。
上表里 msedge 占 2682MB、explorer 占 5874MB —— 前者该考虑回收，后者**绝对不能动**（CPU 155%）。
这是纯内存排序工具**必然给出错误建议**的地方。

### B. 回收（需提权）：释放量 vs 可用内存增量

**这两者必须分开报**，本项目铁律 8 就是为这条立的。

实测反例：**释放 872.8MB 的当天，可用内存只涨了 38MB**。
原因：释放的 Private 里相当部分是「已被系统拿来做后备缓存」的部分，
加上同期别的进程也在涨，差额被吃掉。

所以正确说法是「**释放了 X MB 的 Private/commit**」，
而不是「内存多了 X MB」——后者会误导。

### C. 本项目独有的能力：句柄类问题在「用前」完全看不见

**使用前**：任务管理器按内存排序，Weixin 排第几根本不重要（它的 Private 567MB，不突出）。

**使用后**：
- Weixin 主进程 **191435 个句柄**
- 分解类型：Event 87031 / Token 65949 / Process 33012
- 再往下：Process 里 **29641 个（89.79%）指向已退出的 pid**
- → **结论翻转**：不是 Weixin 的问题，是 **explorer 泄漏崩溃的连带后果**

这个结论**不可能从任何普通内存工具的输出里得到**。

### D. 前后对照总表

| 维度 | 使用前 | 使用后 | 可量化 |
|---|---|---|---|
| 「卡」的归因 | 凭印象 | 家族级 Private + commit + load | msedge −1865MB 回落 / git +512MB 新增 |
| 在干活 vs 泄漏 | 分不清 | CPU 总增量判活 | explorer CPU 155% → 在干活；msedge CPU 0% → 空闲 |
| 句柄类泄漏 | **完全看不见** | 类型分解 + gone/live 分离 | 29641 个指向已退出 pid |
| 趋势 | 无基线 | 自动对比上轮报告 | commit 25830 → 29887MB (+4057) |
| 回收效果 | 说不清 | 释放量与可用增量分开报 | 释放 872.8MB / 可用只涨 38MB |

## 五、自动化现状小结

- **无常驻服务**（对多 agent 电脑是对的：常驻进程本身就要被体检，凭什么豁免自己）
- **3 个计划任务**覆盖：只读体检（每周）/ Codex 沙箱回收（每日）/ 挂死进程回收（每日）
- **回收全部带守卫**，命中即跳过，跳过不算失败
- **默认只读**：所有回收动作不带 `--apply` 只打印建议命令；要执行必须显式加开关

### 一个待修的隐患（已发现，未擅自改）

三个计划任务的 `Execute` 都指向：

```
C:\Users\Administrator\.workbuddy\binaries\python\versions\3.13.12.old.19168\python.exe
```

注意 **`.old.`** —— 这是 WorkBuddy 升级前留下的**旧版本目录**（当前是 `3.13.12`）。
实测**目前仍能跑**（两个目录都是 3.13.14，工具不依赖 psutil，用 PowerShell 取数），
但版本目录一旦被清理，任务就会静默失效。

→ 建议改成 `versions\current\python.exe` 或 `versions\3.13.12\python.exe`。
**这是修改系统计划任务，需你确认后再动。**

## 六、要不要再交给 opencode 复核？

**建议：不要做全面复核，改为做一次定点交叉验证。**

理由：

### 不必全面复核的理由

1. **上一轮 grok 4.7 复核的价值已经被兑现了**——它找出 7 个真 bug，全部已修并复测。
   再来一轮全面复核，边际收益递减。
2. **本轮新增的两个 Skill 是方法论文档 + 一个门禁脚本**，没有复杂逻辑。
   门禁脚本本身**已经跑过双向验证**（第一次跑就抓出 `SOLO_HANDLES_ABS` 缺失，
   补上后 PASS —— 它当场证明自己能抓错）。
3. opencode 的 `.cmd` 包装器**当前是坏的**（路径拼接错误，实测报
   `No such file or directory`），必须直接调 `opencode.exe`。这是额外摩擦。

### 建议做的定点验证（成本低、价值高）

只问三个问题，不问"整体好不好"：

1. `check_skill_consistency.py` 的判据清单**有没有漏掉真实事故中出现过的东西**？
2. 两个 Skill 的**触发词会不会互相抢**？
3. 判据里的**数字**（SOLO_HANDLES_ABS=20000、89.79%、+1022/−3.2）**是否与
   `agent-hygiene` 仓库里的实测值一致**？

第 3 条尤其值得——两个 Skill 现在是**手抄** agent-hygiene 的数字，
**没有机器校验**。这正是本项目铁律 12 说的「同一数字在两份文档出现时必须同步改」。
→ 可以让 `check_skill_consistency.py` 顺带比对仓库里的数字。

### 工具可用性（已实测）

```
opencode.cmd → 坏（路径拼接错误，报 No such file or directory）
opencode.exe → 可用
实测: opencode.exe run -m minimax-cn-coding-plan/MiniMax-M3.1-Flash "只回答两个字：可以"
输出: 可以
```

所以要跑复核，用 exe，别用 .cmd。
