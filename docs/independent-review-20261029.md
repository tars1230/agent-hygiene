## 二、复核方找出的真 bug（已修）

### 🔴 BUG-1：把「存活目标」印成「已退出」（A3 / A8）

**复核方原始输出**：
```
指向已退出进程的僵尸句柄: 29641 个 (占 15.49%)
   pid=13092     21286
   pid=20764      8354
   pid=425444     3334      ← 复核方指出这是活着的 explorer
```
**本项目方独立复测**（`_scratch/verify_grok.py`，独立正则，不复用被测代码）：
```
已退出(Nonexistent) 目标:
   pid=13092       21286
   pid=20764        8354
   pid=28932           1
   合计 = 29641

存活目标:
   pid=425444       3334   explorer.exe(425444)
   pid=29876           4   Weixin.exe(29876)
   ...
=== 3. 泄漏源名单里 425444 到底是什么 ===
Name=explorer PrivMB=139.4 Handles=3776 Threads=100 Start=10/29/2026 10:01:24
```
**根因**：`parse_types()` 把两类目标混在**同一个字典** `proc_refs` 里，
打印时只排除 `"__gone__"` 键，就把剩下的全标成「泄漏源 pid」。
**修复**：`parse_types()` 现在返回三个独立结构 `gone_refs` / `live_refs` / `live_names`，
工具输出分别列出「已退出目标」与「存活目标（带进程名）」。

### 🔴 BUG-2：n≥2 时中位数被离群实例自己抬高（A9）

**复核方原始输出**：
> **n=2 没有特殊处理。** 190000 和 243 的中位数是 95121.5，倍数变成 2.00，`analyze()` 返回 0 条。

**本项目方独立复测**（`_scratch/verify_a9.py`，修复前）：
```
=== 场景 A: 泄漏进程 + 一个正常同 exe 实例 (n=2) ===
  异常候选数 = 0
  => 期望: 应报出 pid=100（190000 是 243 的 780 倍），实际: ❌ 漏报
```
**修复**：改用 **leave-one-out** —— 算某进程的倍数时，参照值取「同 exe **其余**实例」的中位数。
**修复后复测**：
```
  异常候选数 = 1
    100 App.exe 190000 ratio= 781.9 同exe同伴中位数(剔除自身)
```
真实机器验证（`_scratch/verify_a9_real.py`）：
```
[handle] pid=28208  Weixin              handles=191435  burst=788.1x  basis=同exe同伴中位数(剔除自身)  peer_count=5
[handle] pid=404204 WorkBuddy           handles=56366   burst=167.9x  basis=同exe同伴中位数(剔除自身)  peer_count=30
[handle] pid=11788  wetype_renderer     handles=22012   burst=102.9x  basis=全局中位数                   peer_count=1  ← 修正前漏报
```

### 🔴 BUG-3：单实例的绝对下限兜不住（A9 第 9 点）

**复核方原始输出**：
> 单实例 21848 句柄（作者举的 `wetype_renderer`）：**不报**。实测该进程 21889 句柄，相对全局中位数 101 倍，仍低于 50000。注释说绝对阈值能兜住这个例子，阈值实际上兜不住。

**本项目方复测**：确认成立。新增 `SOLO_HANDLES_ABS = 20000`（单实例组专用下限）。
真实机器复测：`wetype_renderer` 22012 句柄 = 全局中位数（214）的 102.9 倍 → **修正后报出**。

**但复核方没提的补充**：绝对下限**不能一味调低**。
`MaintenanceService`（123SyncCloud 服务）12843 句柄 = 60 倍，按倍数早该报——
但它的句柄构成是 **Process 12639 个（98.4%）且全部指向存活进程**（僵尸数 = 0），
属于「服务合法持有大量子进程句柄」，**不是泄漏**。
→ 这正说明**只看倍数会误报**，绝对下限必须配合句柄类型分解一起看。

### 🔴 BUG-4：交叉校验要求完全相等（A8 第 5 点）

**复核方原始输出**：
> 交叉校验要求完全相等。这次 Weixin 多次正好相等。11:16 报告是 Handle 178037、Get-Process 178042，被印成「不一致 ✗」。

**修复**：新增 `cross_check()` —— 枚举前/后各取一次 `HandleCount`，
行数落在区间内即判「一致（落在枚举前后 HandleCount 之间）」。

### 🔴 BUG-5：Δ 比例分母过小 / 突跳阈值固定（A7 / A8）

**复核方原始输出**：
> 分母是 +1 个 Process，这个比例没有意义。
> `d > 500` 在 45 秒间隔上会把大约 +670/分钟的匀速增长标成每一段都是「突跳」。

**修复**：
- `Δ 比例`分母 < 50 时抑制并说明原因；
- 突跳判定改为与**本轮各段速率的中位数**比较，并直接印每分钟速率；
- 「总数在涨」只在 `dt > 0` 时打印，`dt < 0` 打印「在降」。

### 🔴 BUG-6：类型正则截断 / 污染（A8 第 6 点）

**复核方原始输出**：
> 多词类型会被截断。实际有 23 行 `ALPC Port`，正则只留下 `ALPC`。

**修复**：白名单式处理两词类型名 `_TWO_WORD_TYPES = ("ALPC Port",)`。

> 🔴 **但不能笼统放宽成两词** —— 这是本项目方在修复时额外发现的坑：
> `Token  TARS\Administrator:6fa1c` 的第二段是**名字不是类型**，
> 放宽后类型统计被污染成 `Token TARS` / `Key HKLM` / `Process explorer`。
> 第一版修复就是这个错，被自己的验证脚本当场抓到，改成白名单才正确。
> 最终实测输出：
> ```
>   Event                     87031  45.46%
>   Token                     65949  34.45%
>   Process                   33012  17.24%
>   Key                        3822   2.00%
>   ALPC Port                    23   0.01%
> ```

### 🔴 BUG-7：Handle 机制解释错误（A1 / A10）

**复核方原始输出**：
> 不加 `-a` 的尾部是高位句柄，不是停在 4020 号槽位。
> `A6D90: Section ...` / `BB3AC: File (R--) ...`

**本项目方独立复测**（`_scratch/verify_a1.py`，Python `int(x,16)` 数值排序）：
```
不加 -a : 489 行
加  -a : 191448 行

=== 不加 -a 的句柄值统计 ===
  min = 0x1E4 (484)
  max = 0xBBBF0 (769008)
  > 0xFB4(4020) 的行数 = 427  (87.3%)

=== 名字列是否为空 ===
  不加 -a: 有名字 489 / 489
  加 -a  : 有名字 103765 / 191448  -> 无名 87683
```
**根因**：早期版本用 `grep | sort` 做十六进制排序 —— 那是**字符串比较不是数值比较**
（`0xBBBF0` 的字符串序 < `0xFB4`）。**本项目方自己踩了记忆里同类的坑。**
**修复**：文档改述为「只列有名字的句柄」，并把「必须用 Python 数值排序」写进铁律。

## 三、复核方判断不成立 / 部分不成立的部分

### A6：增长速率的精确描述不成立，但底层现象成立

**复核方原始输出**：
> 4 轮 × 45 秒里没有「+2000 突跳」，也没有「+675/分钟」
> 文档自己的端点也算不出 +675/分钟：(186930 − 180800) / (15 − 9) = **1022/分钟**。

**本项目方复测**：复核方的算术正确 —— 文档里那个「+675/分钟」**确实是错的**。
**处置**：文档删除所有写死的速率数字，改为「速率是当次测量的性质，不是常数」，
并要求引用时必须带上当次的原始序列。工具 `--diff` 现在直接印每段速率。

### A7：「增长来自存活子进程」不成立

**复核方原始输出**：
> 跨小时的 Process 增长指向活着的 explorer，不是 WeChatAppEx 子进程。
> 15:02→15:07 的 Process +100 与 425444 的 +100 一一对应。

**本项目方复测**：`verify_grok.py` 证实 425444 是**活着的 explorer**，
其句柄数从 3234 涨到 3334（+100），与同期 Process 总数 +100 一一对应。
**结论**：原结论「增长来自 WeChatAppEx 子进程容器」**是错的**。
**处置**：
- SKILL.md / README.md 删除该归因；
- 工具 `--diff` 现在输出「已退出目标 Δ」与「存活目标 Δ」两张表，
  不再由程序替用户下「来自子进程容器」的结论。

### A5：「96127 记在报告第 43 行」不成立

**复核方原始输出**：
> 「96127 个 Suspended」证据不足。第 43 行没有线程数。
> `reports\` 下 12 份报告都没有 96127 或 96262。

**本项目方复测**：
```
$ grep -rl "96127\|96262" .../reports/
(报告中无此数字)
```
**结论**：复核方正确。96127 / 96262 来自**当时手工执行的 `Get-Process explorer` 命令输出**
（原始输出真实存在，已原样抄录在 README / SKILL 里，可自行复核），
但**不能声称「报告第 43 行记载了它」** —— 报告那一行只有 pid / explorer.exe / Private 8436.5MB 三项。
**处置**：文档改为「来自手工命令输出（已原样抄录），不在任何报告里」。

## 四、这次复核暴露的元问题

1. 🔴 **「自己复核自己」最危险的不是数据错，而是「机制推断错」**。
   本次复核方指出的 BUG-1（把活进程印成已退出）就是一个**方向性错误**：
   顺着「泄漏源」这个既有框架往下推，越推越深，却从没回头检查「这个 pid 真的退出了吗」。

2. 🔴 **同一个坑隔一段时间会再踩**。十六进制排序那个坑，本项目方在别的项目里
   （`grep -c $'\r'` 在 Windows 上给假阳性）已经踩过一次并写进了纪律，
   这次还是在另一个形态下踩了（`grep | sort` 排 hex）。**纪律条目必须写成「怎么判断」
   而不是「别犯什么错」。**

3. 🔴 **文档里的数字会「分叉」**。同一组结论在 README 和 SKILL.md 里各写一遍，
   改了一处忘了另一处，就产生互相矛盾的数字。
   → 已加铁律：**同一个数字在两处出现时必须同步改**，
   并用机器核验脚本（`_scratch/doc_consistency.py`）检查。

4. 🔴 **「结论方向」比「结论数字」更容易蒙混过关**。
   A2/A4 被复核方判「成立」但绝对数已过期；A6/A7 被判「不成立」但底层现象成立。
   → 复核必须**分开问「数字对不对」和「方向对不对」**，两者用不同判据。
