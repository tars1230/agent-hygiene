# Agent Hygiene —— 多 agent 电脑的内存体检

给装了多个 AI agent（WorkBuddy / Codex / Cursor / MiniMax / opencode / cline / 各类桥接…）的
Windows 工作站做定期体检。
**核心立场：只读诊断优先，定点回收其次，通用自动清理永远不做。**

## 铁律（违反 = 结论不可信，全部实测换来的）

1. **默认只读**。任何回收动作只打印建议命令；要执行必须先复述目标进程/PID/服务名并获得用户明确确认。
2. **报占用用 Private/Commit，不用 WS**。WS 会被系统 trim；`SetProcessWorkingSetSize(-1,-1)`
   实测只降 WS 不降 Private（`tools/trim_experiment.py` 可复现）。
3. **「在干活」和「泄漏」不能靠名字/内存量判断**，必须用 CPU 时间采样（GetProcessTimes 多次采样取增量）。
   实测教训：一个 954MB 的 agent 进程看着像泄漏，实际在跑任务（CPU 530 秒）。CPU 持续 >1% = 在干活，别动。
4. **顶层应用「父进程已退出」是常态**（启动器/资源管理器退出），不是孤儿。孤儿只判
   「Electron 子进程（renderer/gpu/utility/crashpad）但宿主 main 已死」。
5. **服务的常驻是设计**（父进程=services.exe / StartMode=Auto），不算泄漏，别建议杀。
6. **不做的事，别再当方案提**：定时 trim（伪优化+伤体验）、Defender 排除项省内存（伪优化，
   排除不减特征库）、盲目关浏览器扩展（真实收益 50–150MB 且伤体验）、任何「动态清理进程」的通用自动化。
7. 每条结论必须能从报告里的原始数字复核；自己估的数字标注「估算」，并尽快用实测替换。
   差值法推出的归属（「A→B 差了 250MB，一定是 X」）必须单独量过才能写进结论。
8. **回收量与可用内存增量要分开报**。实测：释放 872.8MB 的当天可用只涨 38MB，
   因为同窗口别的进程涨了 2.5GB——单点收益必须在静默窗口测，且不承诺「释放 X 内存」。
9. 🔴 **explorer 这类进程的泄漏在任务管理器里几乎看不见**。实测样本：Private 8432MB 而
   WS 只有 452MB，96127 个线程处于 Suspended 状态——**看「内存」列完全正常，吃掉的是 commit**。
   **必须看线程数/句柄数**，阈值：线程 >2 万即异常。只看 WS/「内存」列会漏掉这类最大泄漏。
10. 🔴 **「计划任务失败」和「进程挂死」是两个独立 bug**，别混成一个。实测：DailyBriefing1745
    连续 8 天 LastTaskResult=267014（SCHED_E_TASK_NOT_RUN，因为计划任务上下文里 `git` 不在 PATH，
    报 FileNotFoundError）；同时又有另一批 git 进程因凭据提示被吞而永久挂起。修的时候两个都要改。
11. 🔴 **句柄泄漏是一整类独立于 Private 的泄漏，按 Private 排序的工具必然漏掉**。
    实测：Weixin 主进程 191435 句柄，而 Private 只有 509–586MB（14 份报告采样区间）—— 在任务管理器里看着完全正常，
    但句柄吃的是**内核对象表**，耗尽后 CreateProcess/CreateFile 会全失败。
    **体检报告必须把「线程/句柄」单列一维**，不能只按 Private 排。
12. 🔴 **判「句柄/线程异常」不能用固定阈值，必须用「相对同 exe 中位数的倍数」**。
    实测同一台机器上：System 8582 句柄、msedge 9158、WeChatAppEx 8479 —— 都是正常的。
    而 Weixin 主进程 191435，是同 exe 同伴中位数（243）的 **788 倍**。
    固定阈值（如 3000）会把正常高值全报成泄漏——**这是 SysWatch 这类工具的实际误报来源**。
    🔴 **但倍数判据有两个例外，必须写进实现**：
    ① **同 exe 只有 1 个实例时，中位数 == 它自己，倍数恒为 1.0，这道防线完全失效**。
       实测本机 82~85 个 exe 是单实例，其中 `wetype_renderer` 持 22012 个句柄
       （A9 修复后复测采样值；该值会随时间增长，引用时必须带采样出处）——
       按「≥20 倍」永远查不出来。正确做法：**单实例组(n==1) 退回
       「绝对下限 20000（SOLO_HANDLES_ABS）+ 全局中位数倍数 ≥20x」**。
       🔴 单实例的绝对下限要**单独设**：用 50000 兜不住 22012 这个量级。
    ② 🔴 **n≥2 时「组内中位数」会被离群实例自己抬高，把异常藏住**（2026-10-29 实测）。
       组内 2 个实例、其中一个 190000 句柄、另一个正常 243 → 中位数 95121.5 → 倍数 2.0 → **漏报**。
       必须用 **leave-one-out**：参照值取「同 exe **其余**实例」的中位数，把自己剔除。
    🔴 **兜底参照系不能用高分位**：实测 P99.9 在 539 个进程上等于**最大值本身**
    （被 Weixin 这类离群值污染），拿它当基准等于「和最大值比」= 恒为 1.0，毫无意义。
    用**全局中位数**（不受离群值影响，代表「一台典型进程」）才有判别力。
    🔴 **别把功劳算错**：挡住 msedge（30.9 倍）的是**绝对阈值 50000**，不是倍数；
    被倍数挡住的是 WeChatAppEx（11.4 倍）。绝对阈值与倍数是「与」的关系，各挡各的。
    🔴 **只看倍数会误报**：`MaintenanceService`（123SyncCloud 服务）12843 句柄 = 60 倍，
    但其句柄 98.4% 是 Process 且**全部指向存活进程**（僵尸数 0）→ 合法持有，不是泄漏。
    **绝对下限要配合句柄类型分解一起看。**
13. 🔴 **判「在干活」要用 CPU 总增量，不要用单窗峰值**。实测 Weixin 3 秒窗内偶发突发
    （峰值 38%），但 16 秒总增量只有 3.4%。用单窗峰值会把「偶发活动」误判成「一直在干活」
    → 漏掉真挂死；用总增量才稳。多窗采样：总增量判「在干活」，峰值仅作参考。
14. 🔴 **WMI 的 `CreationDate` 是 `System.DateTime`，PowerShell 默认输出成美式
    `10/21/2026 15:10:32`**，Python `fromisoformat` 解析不了 → 返回 None → 存活时长算成 0 →
    所有「存活时长」守卫形同虚设。必须显式 `$c.ToString('yyyy-MM-ddTHH:mm:ss')`。
    （本项目真实踩过：Weixin 存活 187 小时却报「存活仅 0 分钟」。）
15. 🔴 **「句柄多」不是可行动结论，必须分解到类型层才知道该找谁**。
    实测 Weixin 主进程 191435 个句柄，分解后是：
    `Event 87031 (45.46%) + Token 65949 (34.45%) + Process 33012 (17.24%)`，
    其中 **29641 个 Process 句柄指向「已退出」的进程**（已退出目标 pid：13092 / 20764 / 28932），
    且 65949 个 Token **几乎全是同一用户 `TARS\Administrator` 的重复副本**（LUID 相同）。
    → 这不是「内存不够」，是「每开一个子进程就 DuplicateHandle 一份令牌、进程退出后不 CloseHandle」。
    Event / Token / Process / Key / File 的归属与处置完全不同，不分解就没法派单。
    🔴 **百分比必须写清分母**：僵尸占 Process 类句柄 89.79%（分母 33012），
    占全部句柄 15.48%（分母 191435）。两个数都对，分母不同，引用时必须写清楚。
    🔴 **「已退出」和「存活」必须分开印（2026-10-29 实测踩到的真 bug）**：
       Handle 输出里文本含 `<Nonexistent process>` 才是已退出；**不含就是目标还活着**。
       早期版本把两类混在一个字典里再统一标成「泄漏源」，
       结果把**活着的 explorer.exe(425444) 印成了「已退出」**。
       现在 `parse_types()` 返回 `gone_refs` / `live_refs` / `live_names` 三个独立结构，
       工具输出会分别列出「已退出目标」和「存活目标（带进程名）」。
16. 🔴 **Sysinternals Handle 默认只列「有名字」的句柄，不加 `-a` 会得出完全相反的结论**。
    实测：Weixin 主进程真实 191435 个句柄，`handle64.exe -p <pid>`（默认）只输出 **489 行**
    （全部有名字，最大句柄值 `0xBBBF0`），加 `-a` 才输出 19 万+ 行。
    必须 `handle64.exe -p <pid> -a`，并用 `Get-Process` 的 HandleCount **交叉校验行数**。
    🔴 **交叉校验不能要求完全相等**：枚举要几秒，期间进程会自己开/关句柄。
    正确判据是「行数落在**枚举前 / 枚举后**两个 HandleCount 之间」（本项目 `cross_check()`）。
    🔴 **别用 `grep | sort` 排十六进制**：那是**字符串比较不是数值比较**
    （`0xBBBF0` 字符串序 < `0xFB4`）。早期版本因此误判成「只枚举了前 4020 号槽位」——
    用 Python `int(x, 16)` 重算后，489 行里 **427 行（87.3%）句柄值 > 0xFB4**。
    🔴 **类型正则别笼统放宽成两词**：`Token  TARS\Administrator:6fa1c` 的第二段是**名字不是类型**，
    放宽会把类型统计污染成 "Token TARS"。正确做法是**白名单**精确处理 `ALPC Port` 这类两词类型名。
17. 🔴 **判断「泄漏是稳态还是持续增长」必须采样足够长，且结论要绑定采样窗口**。
    🔴 **速率是当次测量的性质、不是常数**：同一进程不同时段的速率可以差两个数量级甚至变号。
      实测对照（2026-10-29 同一台机器、同一进程 pid 28208）：
      · 早期一次采样：约 +1022/分钟（写死「+675/分钟」是错的，那张表端点自算出 1022）
      · 复核时 4 轮 × 45 秒：约 +20/分钟
      · 复核后 14 轮 × 60 秒（15:31–15:46）：**−3.2/分钟**（中位数 +0.0，无突跳）
      → 结论必须写成「**在 <时段> 的采样里是 <什么>**」，而不是「它 <是/不是> 在增长」。
    🔴 **凡是「泄漏是否还在增长」这类问题，采样必须覆盖到至少一个突跳周期**（≥15 分钟），
      并且**至少做两次类型分解对比**。
    🔴 **「僵尸数不变」只说明「存量僵尸不是增长源」，不等于「增长来自子进程容器」**
      （2026-10-29 独立复核实测纠正）。增长源必须看**逐目标 pid 的 Δ**：
      区分「已退出目标 Δ」和「存活目标 Δ」——两者归属完全不同。
      实测：存活目标的新增**全部指向活着的 explorer(425444)**，不是 WeChatAppEx 子进程。
    🔴 **突跳判定不能用固定阈值**：固定阈值（如 Δ>500）在匀速增长时会把每一段都标成「突跳」，
      毫无信息量。要与**本轮各段速率的中位数**比较，或直接印每分钟速率
      （中位数为负时另走分支，「> 3x 负数」没有意义）。
    🔴 **Δ 比例的分母太小时毫无意义**：以 Process 为基准时，若 Process 只涨了 1 个，
      「Event 30.00」这种数字是噪声，必须抑制（本项目下限 50）。
    工具已内置：`python tools/handle_type_breakdown.py <pid> --diff --interval 60 --rounds 10`
    → 输出逐段增量 + 每段速率 + 逐目标 pid Δ + 首尾对比 + 自动判读。

18. 🔴 **skill 有三份副本，改一份不会同步另外两份**。
    2026-10-29 实测踩坑：仓库里 `skill/agent-hygiene/SKILL.md` 已修正 7 个判据，
    但用户级安装的 `~/.workbuddy/skills/agent-hygiene/SKILL.md` **还是旧版**
    （13 条铁律 vs 17 条），新增的 `leave-one-out` / `SOLO_HANDLES_ABS` /
    「489 行」/「Nonexistent」判据**一条都没有**——下次 agent 加载 skill 会用错判据，
    而且**没有任何东西会报错**。
    🔴 **凡是「同一份内容在多处存在」的地方，都必须有机器校验**：
    本项目已有 `check_doc_consistency.py`，第 4 类检查专门比对「已安装 skill 副本 vs 仓库版」，
    不一致直接 FAIL 并打印修复用的 `cp` 命令。
    → **改仓库里的 SKILL.md 后必须立刻同步安装副本**：
    ```
    cp skill/agent-hygiene/SKILL.md ~/.workbuddy/skills/agent-hygiene/SKILL.md
    python tools/check_doc_consistency.py   # 必须退出码 0
    ```

## 工具（本仓库 `tools/` 目录）

| 工具 | 用途 | 性质 |
|---|---|---|
| `agent_hygiene_audit.py` | 体检：内存压力 + 家族 Top + **线程/句柄维度** + 孤儿/HCS/shim + 空转 vs 干活 + 对比 | **只读** |
| `thread_handle_probe.py` | 线程/句柄探测（一次 PS 调用取全表，~360ms）+ 中位数倍数判据 | **只读** |
| `handle_type_breakdown.py` | 句柄**类型分解**（Event/Token/Process… + 已退出目标与存活目标分列），把「句柄多」变成根因 | **只读**，需 Sysinternals Handle |
| `check_doc_consistency.py` | 文档一致性核验：构成表加总、两份文档同指标、已作废说法残留、**已安装 skill 副本 vs 仓库版** | **只读**，退出码 0 = 全一致 |
| `codex_sandbox_cleanup.py` | Codex 沙箱 VM 泄漏回收（两档 + 四守卫 + 年龄门槛） | 会动服务，需 `--apply` |
| `stuck_process_cleanup.py` | 挂死进程回收（explorer 线程泄漏 / 挂死命令行链 / 句柄泄漏） | 会杀进程，需 `--apply` |
| `hcs_ctl.py` | HCS compute system 枚举/属性（取证用） | list/props 只读 |
| `trim_experiment.py` | 复现「trim 只降 WS 不降 Private」 | 只读 |

仅支持 Windows。报告默认写 `%LOCALAPPDATA%\agent-hygiene\reports\`，回收日志在 `..\logs\`。

## 工作流

1. **先体检**：`python tools/agent_hygiene_audit.py --top 15`（约 30 秒）。
   报告第 4b 节是**线程/句柄维度**——它独立于 Private 排序，专门抓「Private 不大但
   句柄/线程爆了」的那一类；第 4c 节是**句柄类型分解**（需装 Sysinternals Handle），
   把「句柄多」变成可行动的根因。
2. **读报告，按判定说话**：
   - 「在干活(CPU>1%)」→ 不动，如实告知用户这是正在工作的成本。
   - 「空闲/阻塞等待 + Private 大」→ 是缓存/等待，回收收益看 Private，且会立刻被其他进程吃掉。
   - 「孤儿」/「vmmem 无 worker」→ 给定点建议（见配方），等用户确认。
   - 「句柄/线程异常 + CPU≈0 + 存活长」→ 才是真泄漏候选，等用户确认再动手。
3. **定点回收**：只对已知模式的泄漏动手，且永远先演练（不带 `--apply`）再实做。

## 已知泄漏配方

### Codex 沙箱 VM（SavedAsTemplate 孤儿，实测挂 25h / 872.8MB）
```
python tools/codex_sandbox_cleanup.py            # 演练
python tools/codex_sandbox_cleanup.py --apply    # 实清（档1停CodexSandboxService→档2退vmcompute）
```
守卫自动跳过：Codex App 在跑 / 有 Docker、WSL、WindowsSandbox / vmmem 年龄 <2h /
compute system 不止一个或非 SavedAsTemplate。
其它 agent 的泄漏按同一套路适配：**先找守护服务 → 停→验→起回；别用未文档 ABI，别 `Stop-Process` VM 宿主。**
没有真实泄漏样本前，不要预防性地写新配方。

### explorer 线程/句柄泄漏（实测 96262 线程 / 210301 句柄 / Private 8432MB）
> 原始命令输出（可复核，2026-10-29 11:00 前实测）：
> ```
> Get-Process explorer | Select-Object Id,PrivMB,WSMB,HandleCount,Threads,StartTime
>   Id    ProcessName PrivMB  WSMB  Handles  Threads StartTime
>   13092 explorer     8432  260.7  210301   96262  2026/10/24 9:29:57
>
> $p.Threads | Group-Object ThreadState   ->  96267 Wait
> $p.Threads | Group-Object WaitReason   ->  96127 Suspended / 135 UserRequest / 5 EventPairLow
> ```
> ⚠️ **注意：Suspended 占 Wait 的 99.85%，但占全部线程的 99.86%** ——
> 报告里写「96127 个 Suspended 线程」时，**分母是 96262 个线程总数**，
> 两者不是同一个集合，引用时要写清楚，别让人误读成「96127/96267 的 Wait 里有 99.85% 是 Suspended」
> （虽然数值接近，但那是两个不同的分母口径）。
```
python tools/stuck_process_cleanup.py            # 演练
python tools/stuck_process_cleanup.py --apply    # 实清（会关掉所有已打开的文件夹窗口）
```
判据：线程数 ≥20000 且存活 ≥120 分钟。根因是第三方 shell 扩展（IDM / WPS qingnse / WeType / 7-zip
都是嫌疑，但**没有硬证据指向某一个**，不猜）。`NtQueryInformationThread` 反查线程归属在本机被拒
（STATUS_ACCESS_DENIED 0xC0000022），所以不做精确归因，直接重启 explorer。
⚠️ 重启 explorer 会关闭所有文件夹窗口——动手前要告知用户。

### 挂死命令行链（实测：git 挂死链 56 进程 + playwright-cli install-browser 70 分钟）
```
python tools/stuck_process_cleanup.py            # 演练
python tools/stuck_process_cleanup.py --apply    # 实清
```
判据：**按命令行模式匹配**（不是按进程名）+ 存活 ≥60 分钟 + CPU 总增量 <1%。
样本 A：计划任务里的 `git push` 因凭据提示被吞而永久挂起，10/21~10/28 每天 17:45 一批，共 56 进程。
样本 B：`playwright-cli install-browser` 挂死 70 分钟，CPU=0、无网络连接、浏览器已下载完 3.1GB 但进程不退
（链为 `sh.exe` → `node.exe(@playwright/cli)` → 子进程）。
🔴 **不要只按进程名匹配**：原版名单含 `sh.exe`（太宽，任何 shell 都算 git 家族），
而 playwright 链的主体 `node.exe` 又不在名单里 → 漏网。改成匹配命令行里的工具标记。
根治 git 挂死要改根因，不只是杀进程：
① remote 用 `https://github.com:443/<owner>/<repo>.git`（不命中 insteadOf 前缀匹配）
② 脚本里 `git -c credential.interactive=never push` + `timeout=120`
③ git 不读 Windows 系统代理 → 必须显式 `-c http.proxy=http://127.0.0.1:<port>`
④ 脚本必须**失败时返回非零退出码**，否则计划任务 LastTaskResult=0 = 失败被完全吞掉

### 句柄泄漏（实测 Weixin 主进程 191435 句柄 / 同 exe 同伴中位数的 788 倍）
```
python tools/stuck_process_cleanup.py            # 演练（只报告）
python tools/stuck_process_cleanup.py --apply --kill-handle-leak   # 实清（不可逆！）
python tools/handle_type_breakdown.py 28208       # 句柄类型分解（定根因）
```
判据：句柄 ≥50000 **且** 相对同 exe 同伴中位数 ≥20 倍 **且** CPU 总增量 <1% **且** 存活 ≥60 分钟。
（单实例组(n==1) 用「句柄 ≥20000 + 相对全局中位数 ≥20 倍」，见铁律 12。）
🔴 **这个配方默认只报告不杀**，与前两个不同：杀 explorer 只是关文件夹窗口（可恢复），
杀 Weixin 主进程会丢失**登录态 / 未发送消息 / 小程序容器**——代价不可逆。
所以必须显式加 `--kill-handle-leak` 才动手，且仍受全部守卫约束。
实测中它正确地**放过了 WorkBuddy 宿主**（5.6 万句柄 = 168 倍，但 CPU 在干活）。

**已定根因（2026-10-29 实测到句柄类型层，不是推测）**：
Weixin 主进程 191435 个句柄的构成 =
`Event 87031 (45.46%) + Token 65949 (34.45%) + Process 33012 (17.24%) + Key 3822 (2.00%) + 其余 1148`。
- **Process 33012 个里 29641 个（89.79%）指向「已退出」的进程**，
  已退出目标只有 3 个 pid：**13092 (21286) / 20764 (8354) / 28932 (1)**。
  🔴 **百分比必须写清分母**：占 Process 类句柄 89.79%（分母 33012）、
  占全部句柄 15.48%（分母 191435）——两个数都正确，别混用。
- **Token 65949 个几乎全是同一个用户 `TARS\Administrator` 的重复副本**（LUID 全同 = `6fa1c`）。
- 全系统扫描（`handle64 -a`）确认：**这些 pid 被 15+ 个互不相关的进程**
  同时持有僵尸句柄（Weixin 28208 / WorkBuddy 404204 / 11788 / WeChatAppEx 16396 / …），
  合计 4 万+ 个 —— **不是单个应用的 bug，是共享资源的泄漏被所有使用者分摊**。
- **pid 13092 就是那个 explorer.exe 线程泄漏样本**（Private 8436.5MB / 96127 个 Suspended 线程，
  见报告 hygiene-20261029-092521.md 第 43 行 —— 🔴 **该行只支持 pid / explorer.exe / Private 8436.5MB 三项，
  96127 这个数字不在任何报告里**，来自当时手工执行的 `Get-Process explorer` 原始输出，
  已原样抄录在 README 与本文件里，可自行复核，但**不能声称报告记载了它**）。
  它崩溃退出后，多个子进程各留了一份指向它的句柄。
- 🔴 **「已退出」与「存活」必须分开**（2026-10-29 实测踩到的真 bug，已修）：
  早期版本把两类混在一个字典里统一标成「泄漏源」，结果把**活着的 explorer.exe(425444) 印成了「已退出」**。
  Handle 输出里文本含 `<Nonexistent process>` 才是已退出；**不含就是目标还活着**。
  现在 `parse_types()` 分 `gone_refs` / `live_refs` / `live_names` 三张表，工具分别打印。
  实测 Weixin 的存活目标：**explorer.exe(425444) 3334 个**（占存活目标 98.9%）、其余是 Weixin/WeChatAppEx 各 2~4 个。
- 🔴 **「僵尸数不变」不等于「增长来自子进程容器」**（2026-10-29 独立复核实测纠正）：
  僵尸数恒为 29641 只说明**存量僵尸不是增长源**；新增的 Process 句柄实测**全部指向活着的 425444（explorer）**，
  不是 WeChatAppEx 子进程。**增长源必须看逐目标 pid 的 Δ**，不能凭机制猜。
  工具 `--diff` 模式现在直接输出「已退出目标 Δ」与「存活目标 Δ」两张表。
- 🔴 **增长率实测（2026-10-29 15:31–15:46，14 轮 × 60 秒独立采样）**：
  总句柄 191441 → 191393（**−48**），平均 **−3.2 个/分钟**，各段速率中位数 +0.0，
  最小/最大段速率 −51.0 / +9.7，**无突跳**。
  僵尸句柄 29641 → 29641（**Δ = 0**）；存活目标 3371 → 3373（**+2，全部是 explorer(425444)**）；
  已退出目标逐 pid Δ = **无**。
  → **该时段是稳态**（甚至略降）。
  🔴 **速率不是常数**：同一进程另一次采样约 +1022/分钟、另一次约 +20/分钟。
  **结论必须绑定采样窗口**写成「在 <时段> 的采样里是 <什么>」，不能写成「它 <是/不是> 在增长」。
  🔴 **方法论教训（这条保留，它是对的）**：单次采样可能给「稳态」也可能给「持续增长」，
  取决于窗口落在哪个相位。凡「是否还在增长」必须采样 ≥15 分钟并**多次复测**。

**这条的价值**：只看「句柄数」只能得出「Weixin 有问题，杀了吧」；
分解到类型层才得出「是 explorer 泄漏的连带后果，存量治本在 explorer」。
**这就是本工具比 SysWatch 等竞品多出来的那一层。**

## 与同类工具的差异（为什么不用现成的）

调研过的同类项目（2026-10）：

| 工具 | 定位 | 为什么不直接用 |
|---|---|---|
| **SysWatch**（GitHub） | 最接近的同类：psutil + Flask + AI 建议，能报「句柄泄漏 / 线程爆炸」 | **只读，永不处置**；判据是固定阈值（句柄>3000 / 线程>100），实测会把 System(8582)/msedge(9158) 一起误报；重度依赖 AI API |
| **WinMemoryCleaner** | 托盘 RAM cleaner（5000+ stars） | 口径是「trim 工作集」= 已被本项目实测证伪（只降 WS 不降 Private） |
| **Process Hacker / System Informer** | 进程管理器 | 只做**观察**，没有泄漏判定与定点回收；内核驱动带来权限与安全负担 |
| **wtop**（Rust TUI） | htop for Windows，线程/句柄面板做得很好 | 纯交互式 TUI，不产出可复核的**报告**，也不做处置 |
| **Dr. Memory** | DynamoRIO 内存调试器，能查 handle 泄漏 | 需插桩、面向 C/C++ 开发者、不是常驻系统工具 |
| **psleak** | Python C 扩展的泄漏回归测试框架 | 测试框架定位，不面向「系统级进程体检」 |

**我们独有、现成项目都没有的组合**：
Private/commit 口径 + **线程/句柄独立维度** + **相对同 exe 中位数倍数**判据（消固定阈值误报）
+ **CPU 总增量交叉验证**（区分在干活 vs 泄漏）+ **句柄类型分解定位根因**
+ 配方制定点回收 + 只读体检 + 计划任务闭环。

🔴 **句柄类型分解是最大的差异化点**。所有竞品最多只能告诉你「这个进程句柄很多」，
本项目能告诉你「**是哪种句柄、泄漏源是哪些已退出的 pid、被多少个进程分摊**」。
实测价值：把「Weixin 19 万句柄，杀了吧」变成
「explorer(pid 13092) 泄漏崩溃导致 15+ 个进程各留僵尸句柄，治本在 explorer」。
这个结论**不可能**从任何竞品的输出里得到。

**从它们借鉴的**：
- SysWatch 的「线程/句柄维度」思路 → 变成我们体检报告的第 4b 节（但判据换成中位数倍数）
- wtop 的「线程/句柄面板」呈现方式 → 变成 Top 线程 / Top 句柄两张榜
- WinMemoryCleaner 的「排除列表 / 阈值分级」产品形态 → 变成守卫 + 分级阈值
- Process Hacker 的「进程树 + 句柄检查」→ 变成孤儿判定与家族分组
- **Process Hacker 的「查看句柄详情」→ 变成 Sysinternals Handle 的类型分解（`handle_type_breakdown.py`），
  但加了三件它们没有的：`-a` 全量枚举的坑位警告、与 Get-Process 的交叉校验、僵尸进程句柄聚类**

## 输出格式要求

向用户汇报时：判定 + 依据（原始数字）+ 建议命令三者齐备；不确定的写「待验证」，估算的标「估算」；
「可用内存低」≠「有泄漏」，先查在不在干活；不奉承、不渲染，直接给结论。
